# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

fivenines-agent is a monitoring agent that collects server metrics and sends them to the fivenines API (https://fivenines.io). The agent runs continuously, probing system capabilities and collecting various metrics at configurable intervals.

## Development Commands

### Setup
```bash
# Install dependencies using Poetry
make install
```

### Code Quality
```bash
# Run linters (isort, black, flake8, mypy, bandit)
make lint

# Auto-format code (isort, black)
make format

# Run tests with coverage (requires 100% coverage)
make test

# Run a single test file
poetry run pytest tests/test_collectors.py -v
```

### Build Binary
```bash
# Build standalone executable for Linux (uses PyInstaller)
./py2exe.sh
```

The build process creates a self-contained binary at `./dist/linux/fivenines-agent-linux-*/` that includes all dependencies (libvirt, libcrypt, etc.) for compatibility with CentOS 7+.

### Running the Agent
```bash
# Run directly with Poetry
poetry run fivenines_agent

# Run with dry-run mode (collects metrics once and exits, prints JSON to stdout)
poetry run fivenines_agent --dry-run

# Check version
poetry run fivenines_agent --version
```

## Architecture

### Core Components

**Agent Loop (`agent.py`)**
- Main orchestrator that runs the collection loop
- Handles signals (SIGTERM, SIGINT for shutdown; SIGHUP for capability refresh)
- Collects static info once (version, uname, boot time, capabilities, user context)
- On each iteration: collects configured metrics, serializes + gzips the payload (`serialize_payload`) and enqueues the compressed blob, sleeps until next interval; a payload that fails JSON serialization drops that tick with an error instead of crashing the agent, and the full-payload debug dump is gated on `debug_enabled()`
- Bounds the server-pushed `ping` map before its sequential loop (hostile or fat-fingered config must not stretch a tick past `WatchdogSec=90`): at most `MAX_PING_TARGETS` (10) targets per tick, picked through a rotating start offset so an over-cap map still cycles through every target across ticks; region/host strings over `MAX_PING_FIELD_CHARS` (200) are dropped; and the whole loop runs under a `PING_LOOP_DEADLINE` (30s) wall-clock budget, because `tcp_ping`'s 5s timeout does not cover DNS resolution, so the count cap alone is not enough
- Manages graceful shutdown with proper cleanup

**Permission Probing (`permissions.py`)**
- Detects available monitoring capabilities at startup based on file permissions, sudo access, and group memberships
- Re-probes automatically every 5 minutes or on SIGHUP signal to detect permission changes; between full probes, a capability that is enabled in config but keeps probing False is re-probed with exponential backoff (60s base, 120s cap) instead of every tick, so a permanently-missing permission stops costing a subprocess spawn per tick while a just-granted one still appears within ~2 minutes (SIGHUP forces an immediate full probe)
- Capabilities include: core metrics (always available), hardware sensors, storage (SMART/RAID), services (Docker/QEMU/Proxmox/systemd), kernel surfaces (cgroup, tri-state "v1"/"v2"/None), security (fail2ban), VPN (`wireguard`, probed via the EXACT `sudo -n wg show all dump` argv the collector runs -- probing anything shorter would report available where the real dump is denied; `openvpn`, probed by `openvpn.probe_management_access()` -- the probe body lives in the collector's own module so the two cannot drift, and it CONNECTS to each discovered management socket and reads the daemon's unsolicited `>INFO:` greeting rather than calling `os.access()`, because the socket is created mode 0777 and every local user passes a file test on a socket whose every read is refused), logs (`journald` read access, probed via `journalctl -n 0`), etc.
- A capability normally GATES its collector (`collectors._is_capability_gated`: present-and-False -> the key is omitted from the payload). `collectors.CAPABILITY_GATE_EXEMPT` opts a key out of that, for collectors whose contract is "a privilege failure is a null, not a missing key" -- today `wireguard` and `openvpn`. For those, the capability is informational: banner + `pending_capabilities` + reason, nothing else
- `collectors.CAPABILITY_NULL_WHEN_UNAVAILABLE` is the NARROWER subset of the exempt set whose collector is additionally SKIPPED (reported as a bare null) once the probe has read its capability False. It is a cost optimisation, not a contract, and it applies only where running anyway is actively HARMFUL: `wireguard` is in it because each doomed `sudo -n` writes an auth-log failure (~1440/day, a standard fail2ban/Wazuh alert signature). `openvpn` is deliberately NOT in it -- its read is a glob plus a connect with nothing to spam, and skipping it would be WRONG rather than merely wasteful, because only the collector can tell `{"instances": []}` ("no OpenVPN here", the prune-all) from `None` ("OpenVPN running, no readable socket") and the probe reports False for both
- Prints a capabilities banner showing what features are available/unavailable with hints

**Synchronizer (`synchronizer.py`)**
- Background thread that sends collected data to the fivenines API
- Fetches configuration from server before starting metric collection
- Handles retries with linear backoff (`retry_interval * try_count`)
- Metric payloads arrive pre-compressed from the agent loop (see SynchronizationQueue); dict payloads (config fetch, logs, image packages) are gzipped here at level 6 (`GZIP_LEVEL`)
- Uses custom DNS resolution with IPv4/IPv6 fallback, backed by a TTL-honoring in-memory DNS cache that is flushed on any resolution failure so a cached negative answer can never pin the agent offline
- Reuses one persistent HTTPS connection per thread (`auto_open=0`, so a server-side close can never bypass the custom resolver, the certifi trust root, or a custom port): a stale kept-alive socket is rebuilt once without consuming a retry, while an HTTP-status error keeps the healthy connection instead of reconnecting against an already-struggling API
- The token swap writes `TOKEN` owner-only (see Config-Dir State Files under Important Patterns): a reader with the per-host token can POST get_config and receive every service credential the config carries

**SynchronizationQueue (`synchronization_queue.py`)**
- Thread-safe queue with maxsize limit for buffering collected metrics, held as gzip blobs compressed at enqueue time so an API-outage backlog costs a few MB instead of hundreds of MB of raw payload dicts
- Prevents memory exhaustion if API is unreachable

**Log Uploader (`log_uploader.py`, `log_capture.py`)**
- Dedicated `LogUploader` worker thread + bounded queue that upload incident log-capture bundles to `/logs` via `Synchronizer.send_logs`, kept off the metric-collection loop so a slow/large upload never stalls collection, `/collect`, or the systemd watchdog
- `CaptureCoordinator` applies the backend `capture_logs` command with a capture_id nonce + on-disk `last_capture_id` persistence: each command fires exactly once and never replays after a `Restart=always` restart; `last_served` advances only after a confirmed upload, so a failed capture retries
- Part of log-monitoring V1; inert until the backend implements the `/collect` `capture_logs` command and the `/logs` endpoint

**Local Journal Allowlist (`journal_policy.py`)**
- The host owner's veto over which unit journals the agent may read, read from `journal_units.allow` in the config dir. The backend's `logs.units` list is the SERVER's policy; this is the one the operator controls, and it is INTERSECTED with the server's, never unioned -- it can only remove access
- Absent file -> no local policy (the default; existing installs are unchanged). Present -> only matching units. Present-but-empty -> nothing. Unstattable/unreadable -> nothing, warned once: a policy that exists but cannot be applied must never read as "no policy"
- Enforced at all four journal reads: `logs.collect_log_signals` (filter), `log_capture.evaluate_and_enqueue` (filter, feeding the coordinator's existing default-deny), `logs._capture_entries` (the choke point where journalctl is actually spawned -- the backstop no future caller can bypass) and `systemd.SystemdCollector._journal_tail` (the failure drilldown ships redacted journal content off-box too, so it is bounded by the same file)
- Patterns are globs; a name with no unit suffix gets systemd's implicit `.service` on BOTH sides of the match, so `nginx` and `nginx.service` are one entry. A name the SERVER sent is accepted only if it matches systemd's legal unit-name charset (`[A-Za-z0-9:_.\@-]`, `_UNIT_NAME_RE`) -- an ALLOWLIST, because the invariant is that the string the policy authorizes is the string journalctl READS, and journalctl rewrites everything else into an escape: a glob is expanded, `/var/log` resolves to `var-log.mount`, `nginx ` to `nginx\x20.service`, `app-+.service` to `app-\x2b.service`. Each of those reads a unit the policy never saw, so enumerating bad characters loses the race by construction. The charset is necessary but not sufficient: systemd appends `.service` to anything its own validator rejects, so the unit-name SHAPE is checked too (`name[@instance].suffix`, non-empty name part, non-empty template prefix) -- `.mount` would be read as `.mount.service` and `@foo.mount` as `@foo.mount.service`, while `.hidden.service` and `-.mount` pass through untouched and must be allowed. Also refused: a dangling symlink (a broken policy is not an absent one), a non-regular file (open() on a FIFO blocks the watchdog-bounded loop forever), a file over `MAX_FILE_BYTES` (truncating a blob can leave a partial `*.service` -> `*`, which WIDENS), and a unit name over `UNIT_NAME_MAX` (255, systemd's own limit, checked on the NORMALIZED name too since the implicit `.service` can cross it). `filter_units` returns (allowed, refused) and `logs` ships `refused_units` in the payload, because `units: {}` is byte-identical to "every unit was healthy". The server's list is itself bounded per call by `MAX_FILTER_UNITS` (200, the `MAX_PING_TARGETS`/`MAX_RESCAN_SCANNED` posture: each entry costs up to `MAX_PATTERNS` fnmatch calls on the watchdog-bounded loop), and everything past the cap joins `refused` rather than vanishing -- a server list long enough to hit it would otherwise drop the operator's genuinely-allowed units with no line anywhere
- stat-identity cached including st_mode and st_ctime_ns (chmod changes neither mtime, size nor inode, so without them a fixed 0600 policy would stay refused forever), reset on SIGHUP. The complementary, stronger control is removing journal access outright (`SupplementaryGroups=` drop-in), documented in the unit and the README

**Out-of-band Upload Workers (`queue_uploader.py`)**
- `QueueUploader` is the shared thread body for every off-loop uploader: bounded-queue drain, `None` shutdown sentinel, per-job isolation (a bad job never kills the thread), and exactly one `on_success`/`on_failure` callback per job so a coordinator can retire or retry the work item
- Subclasses supply only vocabulary (`label`, `job_id_key`, `payload_noun`). Users: `LogUploader` (`/logs`) and `ImageInventoryUploader` (`/image_packages`)
- Anything slower or larger than a metric payload belongs here rather than on the collection loop (which the systemd watchdog bounds) or the Synchronizer drain

**Image Inventory Worker (`docker_image_inventory.py`)**
- `ImageInventoryUploader` + `ImageInventoryCoordinator`: extraction (N archive fetches + tar parsing) and the `/image_packages` POST run entirely off the collection loop, so a 3-image tick does not extend the tick
- Image digests are immutable, so each is extracted **once per image forever**: done digests persist to `image_inventory_done` (bounded, FIFO-evicted) and survive a `Restart=always` restart. Failures back off exponentially and are given up on after `max_attempts` (in-memory, so a long outage cannot permanently blind an image); a queue-full shed releases the slot without counting an attempt
- `once per image forever` has one escape hatch, and it is server-driven: a transient `api_error` is reported INSIDE a 200, so the digest is marked done and the image would read "not scannable" forever. `ImageInventoryCoordinator.reset()` (via the top-level `rescan_images` config key) re-opens exactly those. A digest with no failure history is re-offered on the same tick the FIRST time it is requested; one the agent had already **given up** on is re-armed onto its retry ladder instead of made immediately eligible. Because the directive is level-triggered (the last `/collect` config is replayed by the Synchronizer during an outage, and a buggy server could re-send it), two agent-side floors keep a stale/looping request from re-extracting every tick: the retry ladder for given-up digests, and a per-digest `rescan_min_interval` (default 1h, `RESCAN_MIN_INTERVAL_SECONDS`) that throttles repeat re-opens even in the immediate `attempts==0` case. `apply_rescan_requests` bounds the untrusted list on three axes -- entries scanned (`MAX_RESCAN_SCANNED`), digests honoured (`MAX_RESCAN_IMAGES`), per-entry length (`MAX_FIELD_CHARS`) -- so a hostile config cannot burn the watchdog-bounded collection loop. `_persist` writes via a temp file + `os.replace` under a dedicated lock and re-reads the done set under `_lock`, since `reset()` (collection loop) is now a second writer alongside `mark_done()` (uploader thread)
- Inert until the backend sends the top-level `image_inventory` config key and implements `/image_packages`

**Subprocess Utilities (`subprocess_utils.py`)**
- Critical for PyInstaller compatibility: removes LD_LIBRARY_PATH and other environment variables that can interfere with system commands
- PyInstaller bundles libraries (like libselinux from libvirt) that conflict with system utilities (sudo, smartctl, mdadm)
- Always use `get_clean_env()` when calling subprocess commands
- `get_clean_env()` also pins `LC_ALL=C` and drops `LANGUAGE` (#172), so every command's output is the same whatever the host's language: smartctl formats `User Capacity` with the locale's thousands separator (shipped verbatim as `total_capacity`), zpool before OpenZFS 2.0 writes `45,67% done` under a comma-decimal locale (read as 67 by the zfs parser), systemd < 232 (CentOS 7) writes localized weekdays into `ActiveEnterTimestamp`, sudo translates its diagnostics. Plain `C`, never `C.UTF-8`: GNU gettext still honours `LANGUAGE` under `C.UTF-8`, and it does not exist on CentOS 7; `LANGUAGE` is dropped too because Python's gettext reads it before `LC_ALL` even under `C` (`pro`). The agent's own locale is untouched. A client that picks its output CHARSET from the locale must name it instead: under C MariaDB's `mysql` negotiates latin1, so a non-ASCII byte in any row (a replica's `Last_SQL_Error`) would arrive in the wrong charset -- hence `--default-character-set=utf8mb4` in `mysql.py`, decoded explicitly with `encoding="utf-8", errors="replace"` (never the agent's locale codec, which is the ANSI code page on Windows) so a byte the flag cannot reach never raises and nulls the collector. `tests/test_subprocess_utils.py::test_every_spawn_site_passes_the_clean_env` enforces the rule across `fivenines_agent/*.py`: every `subprocess` spawn passes `env=get_clean_env()` or a name bound only to it (adding a key, like mysql's `MYSQL_PWD`, is fine), `run_privileged` may omit `env=` since it defaults to the clean env, and writing any `LC_*`/`LANG`/`LANGUAGE` key other than `LC_ALL = "C"` (the dpkg/rpm re-pin in `packages.py`) is refused; the two constant macOS-only `os.popen` dev paths in `cpu.py`/`network.py` are outside it. Measured unchanged under C: `systemctl list-units/show/list-dependencies` (with `--plain`; should a systemctl ever ignore it, `systemd._parse_reverse_deps` strips C's ASCII tree glyph pairs `|-`, `` `- ``, `| ` whole, so `-.mount` keeps its dash), `journalctl -o json` and snmpget on Debian 12 (systemd 252), `pro api` on Ubuntu 18.04/20.04 (Python 3.6/3.8)

**Bounded Calls (`bounded.py`)**
- `call_bounded(fn, timeout, name=None)` is the ONE never-wait-past-a-deadline primitive for calls that cannot be interrupted once they block (a root-owned sudo child, a wedged libvirt socket, a kernfs readdir stuck behind reclaim): it runs `fn` on a named daemon thread, returns its value, re-raises its exception on the CALLER's thread (where telemetry and the caller's handlers see it), carries the caller's thread-local log capture into the worker (`debug.adopt_log_capture`, so error lines `fn` logs still reach collector telemetry), and at the deadline raises `WorkerTimeout` carrying the still-running worker. A daemon thread never holds the interpreter's exit, but one stuck in an uninterruptible kernel wait (D state) still delays the process's final exit until that wait ends
- Each caller keeps its own policy for the abandoned worker: `run_privileged` converts it to `subprocess.TimeoutExpired`, the libvirt probe (`_libvirt_probe_thread`), `io_topology`, `qemu` and `pbs` (each a module-level `_stalled_worker`; qemu and pbs bound their WHOLE collection) single-flight on it so a stall leaks one thread, not one per tick. Do not hand-roll another thread-plus-join; a per-collector bound in `collect_metrics` (TODOS.md) is meant to be built on this

**Bounded HTTP Body Reads (`http_body.py`)**
- `read_capped_body(response, max_bytes, timeout_s)` is the one shared bounded read for HTTP collectors fetching server-pushed URLs: the caller issues `requests.get(..., stream=True, allow_redirects=False)` and the body is streamed under BOTH a byte cap (checked chunk-by-chunk, never buffer-then-check) and a wall-clock deadline -- `requests`' scalar `timeout` is a per-socket-op inactivity timeout, so a trickling endpoint never trips it and would otherwise stall the watchdog-bounded collection loop
- Raises `BodyOverBudget` (a ValueError) that each caller maps onto its existing failure contract; the response is closed on every path. Users: `tsdb.py` (8 MB / 15s), `php_fpm.py` (1 MB / 5s), `rabbitmq.py` (16 MB / 20s), `pbs.py` (16 MB / 10s for its group and snapshot listings, 4 MB for its other endpoints, clamped to its deadline; 64 KB for `/version`; 4 KB / 2s for error bodies). `redis.py` applies the same cap+deadline posture to its raw-socket INFO read (1 MB / 5s)
- Any new collector reading a server-pushed HTTP URL must fetch through this posture (streamed, redirects refused, capped) instead of `response.text` / `response.json()`

**Wire/Log Sanitation (`scrub.py`)**
- `scrub_str` / `scrub_message` / `log_safe` / `as_int` / `as_bool`: the one implementation of how an API collector ships or logs a customer-controlled string (UTF-8 repaired, NUL removed, capped; messages prefix-bounded BEFORE `redact()` so a hostile blob cannot make the redaction regexes a CPU sink; control characters collapsed and non-ASCII backslash-escaped on the log path, so print() cannot raise on any stdout encoding -- a Windows service's is the ANSI code page). Shared by `proxmox.py` (which keeps its old private names as aliases) and `pbs.py`; a new API collector uses it rather than a copy

**Environment (`env.py`)**
- Central source for runtime configuration: `api_url()`, `config_dir()`, `dry_run()`, `log_level()`
- Config directory defaults to `/etc/fivenines_agent`; override with `CONFIG_DIR` env var
- `get_user_context()` collects user/group info sent with each payload

**Collector Registry (`collectors.py`)**
- Declarative `COLLECTORS` list maps config keys to `(data_key, callable, pass_kwargs)` tuples
- `agent.py` iterates this registry each tick; `pass_kwargs=True` unpacks the config dict as `**kwargs` to the callable
- Add new metrics here rather than modifying the agent loop

### Metric Collectors

Each metric collector is a separate module that exports functions to collect specific metrics:

- **Core metrics** (always enabled): `cpu.py`, `memory.py`, `load_average.py`, `io.py` (per-disk counters, verbatim `psutil.disk_io_counters(perdisk=True)`, i.e. every `/proc/diskstats` row; plus the separate `io_topology` collector (#155), which reports, keyed exactly like the `io` rows, what each device is STACKED on so the server can total what the physical disks did instead of adding every layer on top (physical device traffic: a RAID1 write still counts twice; see the fixture's `counting_contract`, including its FALLBACK for a host with no physical leaf, e.g. an OpenVZ ploop container). Whole devices are the `/sys/block` entries and carry `{slaves, virtual}`: `slaves` from `/sys/block/<dev>/slaves/` plus an NVMe native-multipath head's `multipath/` links (its hidden `nvmeXcYnZ` path disks carry the same I/O in `/proc/diskstats`, so the head must read as a layer, like a dm-multipath map; only ENOENT there means "not a head"; the links exist since Linux 6.15, so on older kernels -- and for a path whose link was never created -- each hidden path disk (`hidden` reads 1; NVMe is its only user) is attached to the head the kernel named it after: path `nvme{S}c{C}n{H}` belongs to head `nvme{S}n{H}`, both built from instances the kernel allocates, so no device identifier can make it pick the wrong disk; a head that is absent or unreadable gets nothing, and a path still present whose `hidden` cannot be read leaves its head out as unknown, unless `multipath/` already lists it, while one hot-removed mid-walk is still attached because its `io` row was collected that tick), `virtual` = no `device` link (sysstat's definition -- md/dm/bcache/loop/zram/zvol are virtual, a paravirtual vda/xvda is not, and neither is Ceph RBD, whose parent is its rbd bus device -- it is a driver-model fact, not a hardware one; it is what tells a zvol or loop device from a real disk, since neither has slaves). Partitions carry `{partition_of}` and are found STRUCTURALLY (a subdirectory of the disk's entry carrying a `partition` file; the disk-name prefix is only a pre-filter), so a Xen PV `xvda1` with no `xvda` is a whole disk. Sysfs spells `/` as `!` (`cciss!c0d0`), but a `!` can also be literal (md takes any `md_*` name verbatim), so a `!` name is resolved against `/proc/diskstats` (read at most once per walk, only when one appears); a name it cannot place is left out, and so is any layer listing it as a slave (a partial `slaves` list is a false claim). The walk runs in a single-flight daemon worker abandoned after `TOPOLOGY_READ_TIMEOUT` (5s, via `bounded.call_bounded`), because a kernfs readdir can stall for minutes under memory pressure; a device hot-removed between reads is left out rather than read as virtual. `slaves: []` is a positive claim reported only from a successful read: a device whose entry cannot be read is LEFT OUT (unknown -- the server falls back to its name rules for that row), never reported as a leaf. `None` off Linux, when `/sys/block` cannot be listed, or while a stalled read is outstanding; the server treats absent/`None`/`{}` alike as "not reported", never "no stacking". Read every tick, uncached (~40us per device measured; membership changes without the device set changing, e.g. a pvmove). Contract: `tests/fixtures/io_topology_contract_payload.json`), `network.py` (per-interface byte/packet/error/drop counters, plus Linux bridge detection, `interface_type` bridge/physical/virtual, `network_link_speed_bps` from `/sys/class/net/<if>/speed`, and `bridge_member_count` so the backend can compute per-interface saturation), `partitions.py`, `files.py`, `ports.py`, `processes.py`, `temperatures.py`, `fans.py`
- **Hardware/GPU**: `gpu.py` (NVIDIA GPU metrics via `pynvml`, registered under the `nvidia_gpu` config key; the NVML session is initialized once per process and kept alive across ticks -- a session-level failure such as a driver reload tears it down so the next tick re-initializes cleanly)
- **Storage**: `smart_storage.py` (requires sudo smartctl), `raid_storage.py` (requires sudo mdadm), `zfs.py`
- **Services**: `docker.py` (per-container state + metrics: status/health/exit-code/OOM/restart-count for every container from its first tick, plus running-container CPU/memory/block-I/O; keyed by full container id; a per-thread cached Docker client (10s per-API-call timeout, `CLIENT_TIMEOUT`) plus a 25s wall-clock collection budget (`COLLECT_DEADLINE`) bound a wedged daemon under the systemd watchdog; `docker_metrics` returns `None` on daemon-unreachable, budget exhaustion, or a mid-pass transport error -- never a partial container map -- so the server never prunes on error, `{}` only when genuinely zero containers), `qemu.py` (libvirt read-only connection; the configured `uri` is checked against an agent-side allowlist BEFORE any libvirt call (agent #142): only `qemu:///system`, `qemu:///session` and `qemu+unix:///...` with no host component and at most `?socket=<file inside /run/libvirt/, /var/run/libvirt/ or $XDG_RUNTIME_DIR/libvirt/>` + `?mode=auto|direct|legacy` are opened (a `;` in the query is refused so the agent and libvirt never parse a query differently), because a libvirt URI also selects the TRANSPORT and `ext`/`ssh`/`libssh`/`tcp`/`tls` run a local command or dial out regardless of `openReadOnly()`. A refused URI logs its reason at error level once per CHANGE of refused URI and at debug while the same one repeats (the config is level-triggered and the collector is re-instantiated per tick; an accepted URI clears the register, so a re-introduced bad URI is an error again) -- the reason only, never the URI or any value from it; the scheme is echoed only when it is a libvirt spelling, since those lines reach the journal and the error telemetry, and URIs over `LIBVIRT_URI_MAX_CHARS` are refused before parsing. A refused URI never reaches libvirt and reports `None`. `None` is also reported on a failed connection or domain listing, and when a listed VM cannot be read: `_collect_domain_metrics` returns False when UUIDString/name/state() raises anything but `VIR_ERR_NO_DOMAIN` (the one VM that may be left out, undefined after listAllDomains), because a restarted daemon makes every later VM fail and a short list reads as VMs gone -- this covers a proxied connection too, where `virtproxyd` keeps the agent's own socket open; `conn.isAlive()` (local, no RPC) is read after the walk as the complement on a direct connection -- with no event loop in the agent it only reports a transport failure an earlier call already hit; `[]` means libvirt listed zero VMs (the docker "report everything or null" contract). No libvirt call carries a timeout, and each monitor call on a VM whose QEMU monitor is stuck waits up to 30s for the domain job lock (#171), so the collection is bounded twice: the whole of it (open, list, per-domain loop, close) runs on a single-flight `bounded.call_bounded` worker abandoned after `COLLECT_TIMEOUT` (15s) -> `None`, no second worker while it is still blocked; and inside it every libvirt call on a domain goes through `_Budgeted`, which checks `COLLECT_BUDGET` (10s) first and raises `_BudgetSpent` once it is spent -> `None`, never the VMs collected so far, with an error line naming where the budget ran out and how many VMs were done (`QEMUCollector.progress()` over one `position` tuple assigned whole: the budget line names a VM, the open, the listing or the uptime scan -- an open that spent the budget stays reported as the open, and a budget the last VM's final call spent is caught before the scan starts, so it is reported at that VM; the tick's timeout line can also name the close. A stuck VM repeats its name on every attempt, a host too large for the budget does not). The scan re-checks the budget after every process (the last one included), and skips a pid whose start time changed while its cmdline was read (PID reuse mid-read). It keeps only the running VMs' UUIDs, refuses a `-uuid` argument over `_UUID_MAX_CHARS` before copying it, and reads each command line straight from `/proc/<pid>/cmdline` through `_read_cmdline`, at most `_CMDLINE_MAX_BYTES` (256 KiB; a longer one is skipped, unread past that) -- never psutil's `cmdline()`, which reads, decodes and splits the whole thing first: any local user can make their command line megabytes long and start processes with `-uuid` arguments of any size, so an unbounded read or keeping every distinct UUID let them grow the agent's memory. Linux only, like the libvirt collection. `_BudgetSpent` is a BaseException (the asyncio.CancelledError reasoning) because every per-metric helper catches `Exception` and would otherwise log it and make the next call. 10/15s rather than docker's 25s because every self-bounded collector shares ONE `WatchdogSec` window (the watchdog is fed only around the whole pass). ### Configuration

- Agent reads `TOKEN` file from config directory (default `/etc/fivenines_agent`, `~/.local/fivenines` for user install, overridable via `CONFIG_DIR`)
- The config dir also holds `journal_units.allow`, the OPERATOR-written (never agent-written) local journal allowlist read by `journal_policy.py`
- Configuration is fetched from the API server on startup and includes:
  - `enabled`: whether collection is active
  - `interval`: seconds between collections (default 60)
  - Feature flags for each metric type (cpu, memory, etc.)
  - Service-specific config (e.g., redis host/port, `docker.socket_url` which drives both per-container state and metrics collection, `qemu.uri` which is subject to the agent-side libvirt URI allowlist in `qemu.py` -- the backend restricts it too, but the agent does not rely on that)
  - `request_options`: timeout, retry count, retry interval
  - `packages.scan`: triggers package inventory sync with hash-based deduplication
  - `image_inventory`: **TOP-LEVEL** truthy flag enabling Docker image OS-package extraction (uploaded to `/image_packages` off the collection loop). It must NEVER be nested under `docker`: `collectors.py` splats `config["docker"]` as `**kwargs` into `docker_metrics`, so a new nested key would raise `TypeError` on older agents, be swallowed into `data["docker"] = None`, and -- with the server's never-prune-on-null rule -- freeze container-state rows fleet-wide. Requires `docker` collection to also be enabled, since the digest set is derived from `data["docker"]["containers"]`
  - `rescan_images`: **TOP-LEVEL** bounded array of image digests the server wants re-inventoried (server issue #676), same splat-safety rule as `image_inventory`. The server sends only `api_error` digests this host runs, past its own 6h backoff; the agent drops them from `image_inventory_done` so the normal selection path re-offers them. Honoured only while `image_inventory` is on. The directive is level-triggered and untrusted, so the agent does not rely on the server for safety: it caps how much of the list it scans/honours/reads per entry, and floors repeat re-opens per digest (`rescan_min_interval`, default 1h) so a stale directive replayed during a `/collect` outage cannot treadmill re-extraction every tick
  - `pbs`: **TOP-LEVEL** Proxmox Backup Server poll (`host` default localhost, `port` 8007, `token_id`, `token_secret`, `verify_ssl`, `fingerprint`), splatted into `pbs_metrics(**config["pbs"])`, which takes `**_kwargs` so a later key is ignored. Never nested under `proxmox` (that dict is splatted into `proxmox_metrics`). No capability gate and no OS gate (pure HTTP; the PBS may be this host or a remote one)
  - `vllm`: vLLM inference-server poll (`metrics_url`, `auth_header_name`, `auth_header_value`, `verify_ssl`), splatted into `vllm_metrics(**config["vllm"])`. `false` disables it; no capability gate and no OS gate (pure HTTP, the tsdb/nginx posture)
  - `sglang`: SGLang inference-server poll, same four keys and same posture as `vllm`, splatted into `sglang_metrics(**config["sglang"])`; `metrics_url` defaults to the SGLang API server port (`http://127.0.0.1:30000/metrics`). `false` disables it
  - `systemd`: unit collection config (`unit_types` as comma-separated string or list; `scan` triggers inventory delta-sync to `/systemd_inventory`)
  - `logs`: continuous log-signal collection (`units` allowlist, `signal_interval_s` window); gated on the `journald` capability
  - `capture_logs`: backend-pull incident capture command (`capture_id`, `unit`, `since`, `lines`, `expiry`); fired exactly once via the capture_id nonce + on-disk persistence, uploaded to `/logs` off the collection loop
  - `io_topology`: **TOP-LEVEL plain boolean** (registered with `pass_kwargs=False`) enabling the block-device topology beside `io`; a separate flag rather than a key under `io` so the server can roll it out independently. Linux-only in effect -- elsewhere the collector reports `None`, which the server reads as "not reported", so stripping it for Windows is optional
  - `wireguard` / `openvpn` / `tailscale`: **TOP-LEVEL plain booleans** (same splat-safety rule as `image_inventory`; all three collectors take no parameters, and all three are registered with `pass_kwargs=False` so a future dict value is ignored rather than splatted into a `TypeError`). `wireguard` and `openvpn` are LINUX-ONLY and belong in the server's `Host::WINDOWS_OMIT_CONFIG_KEYS` so they are stripped for Windows agents (`wireguard` is already there; `openvpn` lands with server #1103 -- tracked in TODOS.md); `tailscale` is cross-OS and never stripped. None of the three is capability-GATED: a privilege failure must surface as `data["wireguard"] = null` / `data["openvpn"] = null` (a collection failure the server skips), not as a missing key. `wireguard` (since #144) and `openvpn` (since #145) ARE capability-probed for the dashboard's pending-capability panel, but both are listed in `collectors.CAPABILITY_GATE_EXEMPT` so the probe can never omit the key. `openvpn` needs no per-host parameters at all -- socket discovery is the runtime-dir glob, so there is nothing for the server to configure beyond the toggle
  - `mqtt`: list of brokers (`broker_id`, `host`, `port`, `tls`, `username`, `password`, `monitors[{id, topic_filter, capture_payload}]`); replaces the agent's MQTT state wholesale each tick (absent/falsy tears all clients down). Consumed as a special-case collector (like `snmp_targets`), not via the COLLECTORS registry

### Installation Types

The agent supports two installation modes:

1. **System installation**: Runs as dedicated `fivenines` user via systemd service (`fivenines-agent.service`) or OpenRC (`fivenines-agent.openrc`)
2. **User installation**: Runs as current user with helper scripts (start.sh, stop.sh, status.sh, logs.sh, refresh.sh)

User context is collected and sent with metrics to help the backend understand permission limitations.

Both system installers verify what they install against the release's signed `SHA256SUMS` before it lands: the agent tarball AND the three startup definitions (`fivenines-agent.service`, `fivenines-agent.openrc`, `fivenines_script.sh`). Those three are published release assets for exactly this reason -- they used to be fetched from `raw.githubusercontent.com/.../main`, a moving branch no manifest can cover, and written straight to their final path, so a compromised mirror could not touch the verified binary but could still choose the `ExecStart` that runs as root at every boot. `install_verified_release_file` (shared, byte-identical across the two SYSTEM scripts; `ci/build-scripts.sh` enforces that with a second list, since the user scripts install no service) stages into the private work dir and only then replaces the file on disk. A host with no `openssl` is FATAL by default (`verify_sums_signature` returns 3, distinct from 2 = "no key embedded", which stays the non-fatal rotation escape hatch); `FIVENINES_ALLOW_UNSIGNED=1` is the documented opt-out, and minimal Alpine images need `apk add openssl`. `verification_preflight` runs that check BEFORE the update script stops the agent: "no openssl" is deterministic per host, so discovering it after the stop would leave every minimal-image host unmonitored on every update. The verified file lands through a sibling temp file inside the DESTINATION directory (chmod + restorecon there, then an atomic same-filesystem rename): a straight `mv` from the /tmp work dir is cross-device, so a crash mid-copy would leave a truncated root-run unit, and the file would keep its tmp SELinux label, which systemd (init_t) cannot read.

All four Linux installers choose their artifact through `select_agent_binary` (shared, in `SHARED_FUNCTIONS`): `uname -m` `x86_64` or `aarch64` only, anything else refused BEFORE the preflight, i.e. before any user, token, directory, download or service stop (#170). The system scripts used to hand every non-`aarch64` host the amd64 build, which verified, installed and then died at exec on every restart. `amd64`/`arm64` are refused too (the FreeBSD/macOS spellings; Linux never reports them). `uname -m` names the KERNEL, so a 32-bit userland on a 64-bit kernel is refused as well when `getconf LONG_BIT` prints exactly `32`: 32-bit Raspberry Pi OS on a Pi 4/5 boots a 64-bit kernel by default and reports `aarch64` over an armhf userland with no arm64 loader. A missing or silent `getconf` never refuses. The premise was checked against the real binaries on an x86_64 kernel (2026-09-29): Debian bookworm's i386 glibc `getconf` and Alpine 3.21's x86 musl `getconf` both print `32`. `ci/test-32bit-userland.sh` (the `shellcheck-scripts` job) re-checks it on every run: the real function inside `i386/debian` and `i386/alpine` images, which run natively on the x86_64 runner, must refuse, and inside their amd64 counterparts must not (a false refusal would block every install). Accepted trade-offs: a biarch/multiarch host (a 32-bit userland with the 64-bit loader installed) is refused although the 64-bit build would run, and so is a 64-bit userland under a 32-bit personality (`linux32`/`setarch`, an LXC container declared i386 over an amd64 rootfs), where `uname -m` says `i686`. The UNRAID boot script sources nothing and carries its own `case` (without the userland check: UNRAID is 64-bit x86_64 only). `ci/test-signing.sh` runs `select_agent_binary` with a faked `uname`/`getconf` and the boot script's `case` with a faked `uname`, and runs the four installers end to end on a faked armv7l inside a PATH stub box.

Every download command an operator is told to paste -- each `wget` in README.md and in the UNRAID hint `fivenines_update.sh` prints -- pins `-O NAME` (a bare file name), fetches exactly one URL, and runs that same NAME (`&& [VAR=...] [sudo ...] bash|sh NAME`); `ci/test-signing.sh` lints both and rejects any other option or spelling (`-qO`, `--output-document`, `-c`), finding the UNRAID hint by its `if [ -f /etc/unraid-version ]` line (#160). Without `-O`, GNU wget never overwrites: a `fivenines_setup.sh` left by an earlier attempt makes it save `fivenines_setup.sh.1`, exit 0, and the `&&` runs the OLD file as root. `-O` does not make a shared directory like `/tmp` safe (a planted file, FIFO or symlink is written into, not replaced), which is what the README note under the standard install is for -- keep it. The pre-release notes in `build-release.yml` follow the same rule (fetching the update script from the build's own commit) but are not linted.

The systemd unit is sandbox-hardened with MOUNT-NAMESPACE/ATTRIBUTE directives only: `UMask=0077` (backstops the 0600 config-dir state files), `PrivateTmp=true` and `ProtectHome=read-only`. Never add a seccomp-backed directive (`ProtectKernelTunables`, `ProtectClock`, `RestrictRealtime`, `SystemCallFilter`, ...) or `NoNewPrivileges`: on a non-root unit, seccomp makes systemd implicitly enable `no_new_privs`, which silently kills every `sudo -n` collector (SMART/RAID/fail2ban, and WireGuard since #144) fleet-wide on systemd >= 228. Also deliberately absent: `ProtectSystem=full/strict` (breaks the TOKEN swap and config-dir state; on systemd < 231 the `ReadWritePaths` exception would be silently ignored) and `MemoryDenyWriteExecute` (pynvml/libvirt load native code via ctypes/libffi). `PrivateTmp` caveats are documented in the unit and README: it hides other services' `/tmp` unix sockets from the agent, and mount-namespace setup is fatal (`226/NAMESPACE`) on OpenVZ-class kernels -- both overridable with a `systemctl edit` drop-in, which survives the updater's unit overwrite. The unit's one group grant is `SupplementaryGroups=systemd-journal` (journal read access), and the unit file itself documents the `SupplementaryGroups=` drop-in that takes it back -- the empty assignment RESETS the list, so `journald` probes false, the `logs` collector is gated off and the systemd failure drilldown ships empty tails. Same drop-in mechanism, same reason it is a drop-in rather than an edit.

## Code Style

- Python 3.10+ required (compatible with 3.10-3.13)
- Code must pass: isort (black profile), black, flake8 (ignore W503, E501), mypy, bandit (config in `pyproject.toml` `[tool.bandit]`)
- Security checks run on every PR and push to main (policy: CONTRIBUTING.md "Security checks"); they only BLOCK a merge once they are listed as required status checks in main's branch protection, which is a repository setting, not something this repo's files enforce. `bandit.yml` fails on any finding not covered by the three documented global skips (B404/B603/B607) or an inline `# nosec BXXX  # <reason>` -- one named test and a reason; a bare `# nosec` fails the job. `ci/check-nosec.sh` (bandit.yml on every PR, and `make lint`) also pins `[tool.bandit]` to exactly those skips and rejects an unknown-ID `# nosec` via Bandit's own blanket counter; bandit.yml proves it still fails on five canaries (an unknown-ID, a bare and a reasonless suppression, a widened `[tool.bandit]`, and a stray `.bandit` INI file, which Bandit would merge even with `-c pyproject.toml`). `codeql.yml` (python + actions, security-extended) fails on ANY result (on a PR, any result in the lines it changes -- CodeQL's diff-informed PR analysis; main and the weekly run cover everything) and lists them in the run summary, because code-scanning alerts are visible only to repo writers: resolve a result by fixing it or by excluding the query in its config with a reason, never by dismissing it in the UI
- Every action in `.github/workflows/` is pinned to a commit SHA with its version in a comment (Dependabot updates both); workflows default to `permissions: contents: read` and every checkout uses `persist-credentials: false` (pre-release deletes its old tag through `gh api`, not a git push). Nothing a branch run can write feeds a v* release: the Synology jobs pull the builder image by the digest `build-amd64`/`build-arm64` output (any branch run can overwrite a tag in our registry), and tag builds build their images with `no-cache` because every branch run can write `:buildcache`. Every download the Linux, Alpine and Synology builds make, and every Python package the Windows build installs, is verified: the libtirpc/libvirt/Python source tarballs against pinned SHA-256 digests (Dockerfile, Dockerfile.arm, py2exe.sh), and every pip install -- build tools, poetry and its dependencies, meson/ninja/docutils, libvirt-python -- from the hash-pinned files in `ci/requirements/` with `--require-hashes --no-deps` (wheels only via `--only-binary :all:`; the libvirt-python sdist and the root project's editable install with `--no-build-isolation`, so no unpinned build backend is fetched). Regenerate those files with `ci/requirements/compile.sh` (uv, universal resolution; Dependabot does not update them, it ignores `--python-version`); a changed pin must still install everywhere with wheels only (manylinux2014 cp310, musl cp311, Windows cp311). `poetry install` in every build runs with `POETRY_INSTALLER_ONLY_BINARY=":all:"` (wheels hash-checked against poetry.lock; an sdist would fetch its build backend unpinned, so it fails instead), and the manylinux libvirt-python pin must equal poetry.lock's (the bake checks it) so poetry skips it rather than rebuilding it. The BuildKit daemon image is pinned by digest too (`BUILDKIT_IMAGE`, passed to every setup-buildx step), and the Alpine binary steps run their just-loaded image with `docker run --pull=never`. The `release` job refuses a v* tag whose commit is not an ancestor of `origin/main` (checkout with `fetch-depth: 0`), matching the merge-first-then-tag procedure. Still resolved by tag or version only: the Dockerfile `FROM` base images, and the Windows WiX toolchain (`dotnet tool install` from nuget.org, whose packages are immutable and repository-signed). The weekly `schedule` run of build-release.yml rebuilds the builder images cold (`COLD_BUILD`), so a broken download or pin fails there before it fails a release. Never add an unpinned action or a `curl | sh` to a workflow -- the release jobs hold the signing key and the R2 credentials. Never name a workflow env var `RCLONE_*` in a step that runs rclone: rclone reads `RCLONE_<FLAG>` variables as its own flags (`RCLONE_VERSION` became `--version` and stopped the v1.19.1 R2 sync)
- Release assets get a build-provenance attestation (`actions/attest`, driven by each publishing job's `SHA256SUMS`), verified with `gh attestation verify` (README "Build provenance")
- `RELEASE_SIGNING_KEY` and the four R2 secrets are secrets of the `release` GitHub environment (deployment policy: `v*` tags only), used by exactly two jobs that declare `environment: release`: `release` and `sync-to-r2`. Never reference them from a job that runs for branches -- that is why `pre-release` is unsigned (nothing reads a pre-release manifest: the installers take `SHA256SUMS` from the latest STABLE release, and a `FIVENINES_AGENT_URL` build is verified only when the operator pins `FIVENINES_AGENT_SHA256`, UNVERIFIED otherwise). `sync-to-r2` refuses to publish an unsigned manifest, since every installer aborts on a missing `.sig` once a public key is embedded
- **ASCII-only characters in codebase** - do not use non-ASCII characters (enforced since v1.4.0)
- Test coverage must be 100%
- Use `from fivenines_agent.debug import log, debug` for logging
- Log levels: 'debug', 'info', 'error'
- Gate expensive-to-build debug messages on `debug_enabled()`: `log()` checks the level only after its argument is built, so an unguarded `json.dumps`/`str()` of a large payload costs CPU on every tick at any log level

## Important Patterns

### Subprocess Calls
Always use clean environment to avoid PyInstaller library conflicts and to run the command in the C locale:
```python
from fivenines_agent.subprocess_utils import get_clean_env
result = subprocess.run(cmd, env=get_clean_env(), ...)
```

**Anything behind `sudo` goes through `run_privileged` instead** (#144):
```python
from fivenines_agent.subprocess_utils import run_privileged
result = run_privileged(["sudo", "-n", *ARGV], timeout=10, stdout=..., text=True)
```
`subprocess.run(timeout=...)` does NOT bound a sudo child: sudo switches to
full root before its sudoers lookup, so the kill CPython issues after the
timeout returns EPERM, that PermissionError escapes the `TimeoutExpired`
handler, and `Popen.__exit__` then waits with no timeout at all -- a wedged
sudoers backend (LDAP/sssd) pins the single-threaded collection loop until the
systemd watchdog SIGABRTs the agent into a `Restart=always` loop. Killing the
process group does not help (root-owned too); NOT WAITING does. `run_privileged`
runs the call in a daemon worker, abandons it at `timeout + 2s`, and raises the
`TimeoutExpired` the caller was promised -- through `bounded.call_bounded`, the
same primitive the libvirt probe and `io_topology` use.
Used by wireguard, smart_storage, raid_storage, fail2ban and `_can_run_sudo`.

### Config-Dir State Files
Create owner-only and heal a pre-existing file's mode; never plain `open(path, "w")`:
```python
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)
os.fchmod(fd, 0o600)  # os.open's mode applies only at creation
with os.fdopen(fd, "w") as f:
    f.write(data)
```
Used by the `TOKEN` swap (`synchronizer.py`), `last_capture_id` (`log_capture.py`) and the `image_inventory_done` temp file (`docker_image_inventory.py`, where `os.replace` carries the temp file's mode onto the final path). The unit's `UMask=0077` backstops a regression, but only on systemd installs.

### Permission-Dependent Features
Check permissions before attempting operations:
```python
from fivenines_agent.permissions import get_permissions
perms = get_permissions()
if perms.get('smart_storage'):
    # Collect SMART data
```

### Signal Handling
- SIGTERM/SIGINT: Sets `exit_event` to trigger graceful shutdown
- SIGHUP: Sets `refresh_permissions_event` to re-probe capabilities without restart; also forces a full systemd inventory resend and re-detects the cached cgroup hierarchy/systemd version; and releases the PBS reads held after a timeout (`pbs.reset_timeout_holds`; every build that can walk then defers the walks of the datastores that armed the hold, unless that would be every datastore, until the group reads have passed them)

### Debug Decorator
Wrap metric collection functions for automatic timing and error logging:
```python
@debug('metric_name')
def collect_metric():
    # Returns metric data
    return data
```

## Binary Build Process

The `py2exe.sh` script creates a standalone Linux binary:
1. Sets up cross-compilation environment for target architecture (amd64/arm64)
2. Creates virtualenv and installs dependencies
3. Builds `libpython3.10.so` from source for PyInstaller compatibility
4. Bundles all dependencies including libvirt 6.10.0, libcrypt, libtirpc
5. Creates onedir distribution with all shared libraries included
6. Output: `./dist/linux/fivenines-agent-linux-*/`

This enables the agent to run on CentOS 7+ without system-level Python dependencies.
